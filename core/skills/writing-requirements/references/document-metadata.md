# Document Metadata Contract

Read the target project's instructions and metadata/status policy before creating or updating an artifact. Project policy takes precedence over template examples; do not invent an enum when no policy is available. Clarify a missing policy before assigning delivery metadata.

- Classify by both `document_type` and owning path using the target project policy. Apply delivery status only to the artifact types allowed by that project. Standards, entities, roles, indexes and reference documents do not acquire delivery status merely because they are edited.
- `status` means delivery of the described capability or change, never document approval, verification result or the fact that text was updated. The template's `draft` is only an example for a newly drafted capability. For an existing capability, use its confirmed delivery state; do not reset it from the template or infer it from a parent/child artifact.
- Emit one literal status value allowed by the project, not a pipe-separated list. Template `draft` is illustrative, not a universal enum or default. Adapt template types, field names, labels, IDs, dates and required fields to the project schema before saving. Keep frontmatter flat and keys snake_case where the project requires them; use the project's date field. Remove unassigned IDs, dates, sample rows and prompts before saving.
- Keep `status` as the single delivery field when that is the project contract; do not introduce a competing `delivery_status`. If existing field semantics conflict with this contract, resolve the project mapping before changing metadata.
- Record approval separately in `approval_status` only when known, using the project-controlled values. Add `Approval Status` to Metadata only when that field exists. Record approver/source/date and the approved revision in content when evidence is available. An unanswered question or self-review result is not approval.
- In the artifact's Metadata table, `Status` mirrors the label for frontmatter delivery `status`. Recognize both `## Metadata` and numbered headings such as `## 1. Metadata` when locating this table. Do not put review status into this row.
- Preserve delivery status on content-only edits. Update the project-defined date field and change history as appropriate; do not create `modified` or `updated` delivery values. Preserve earlier approval evidence and identify the revision it covers; do not claim that evidence approves newly changed content.
- Synchronize current catalog rows by the artifact's exact path/link or ID when changing delivery status. Preserve scope notes and approval evidence when updating a current row. If a cell mixes delivery with notes or approval, separate the information without discarding it. Do not rewrite historical rows, product/HTTP statuses, Open Questions or Decision Logs. Never derive parent or child status automatically.
- API operation and NFR item tracking must name delivery/implementation, approval and verification separately. Use project-controlled delivery values where that concept applies; do not invent a mixed lifecycle enum.
- For standalone Use Cases, resolve the project-supported document type, ID, filename and delivery applicability before adding frontmatter. A Use Case embedded in another artifact uses that artifact's metadata. Do not introduce a `use-case` type unless the project supports it.
- Run project metadata/template/catalog validation after saving. A registered legacy exception is temporary migration evidence, not permission to reuse the legacy value on another file. Do not regenerate a migration baseline to make validation pass.
